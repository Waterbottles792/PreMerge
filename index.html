Under the hood

Two signals, one score

PreMerge runs two independent analyses on every branch pair, then combines them into a single weighted risk score with a plain-English explanation.

Signal 1 Direct Overlap

Both branches are diffed against their common merge-base using git diff -U0. PreMerge parses every hunk header and checks whether the line ranges intersect. This catches both file-level and line-level conflicts — the same thing git would find at merge time.

Signal 2 Historical Coupling

PreMerge walks your entire commit history and builds a co-occurrence matrix: which files always change together? It scores every file pair using Jaccard similarity — if branch A touched auth.py and branch B touched session.py, and those two files co-change in 9 of 10 commits, that's a hidden conflict.

Scoring formula

risk(A, B) = 0.5 × line_overlap_score # do they edit the same lines?
           + 0.3 × file_overlap_score # do they touch the same files?
           + 0.2 × coupling_score # do they touch files that co-change?

All three weights are tunable in premerge.config.json. The formula is transparent — you can always see exactly why a pair scored what it scored.

What you get

Everything in one command

No setup, no external services, no accounts required.

🔍

Line-level conflict detection

Parses git diff -U0 hunk headers to find branches editing intersecting line ranges — not just the same file.

🧠

Hidden coupling detection

Catches logical conflicts with zero textual overlap. If two files always change together in history, PreMerge flags them — even when git wouldn't.

⚡

SQLite cache

Coupling analysis is cached by HEAD commit hash. Unchanged history = instant re-runs. CI warm runs complete in under a second.

🚦

CI risk gate

--fail-above 0.6 exits 1 when any pair exceeds the threshold. Turns PreMerge from a report into a hard pipeline gate.

💬

Plain-English explanations

Every score comes with a reason: which file, which lines, which historical pair triggered it. No black box.

🎛️

Tunable weights

Adjust the three signal weights in premerge.config.json. Or use --depth to limit history on large repos.

📦

Minimal footprint

Two runtime dependencies: click and rich. Git is driven via subprocess. GitHub API via stdlib urllib.

🐳

Docker ready

Mount any repo into the container and run — no Python setup needed. The image bundles Python, git, and the CLI.

🔬

Hermetic test suite

Tests build real throwaway git repos in temp directories. No fixtures on disk, no network. Works on any machine.

Get started

Up in 30 seconds

Requires Python 3.11+ and git on your PATH.

# clone and install
git clone https://github.com/Waterbottles792/PreMerge.git
cd PreMerge && pip install -e .

# analyze every branch pair in your repo
premerge analyze

# all branches vs main
premerge analyze --base main

# one specific pair
premerge analyze feature-a feature-b

# CI gate: exit 1 if any pair scores >= 0.6
premerge analyze --base main --fail-above 0.6

# limit history depth on large repos
premerge analyze --depth 1000
# build the image once
docker build -t premerge .

# mount any repo and analyze
docker run --rm -v "$(pwd)":/repo premerge analyze --repo /repo

# any other repo on disk
docker run --rm -v /path/to/other/repo:/repo premerge analyze --repo /repo
# .github/workflows/premerge.yml
name: PreMerge Conflict Risk Check

on:
  pull_request:
    types: [opened, synchronize, reopened]

jobs:
  premerge:
    runs-on: ubuntu-latest
    permissions:
      pull-requests: write
    steps:
      - uses: actions/checkout@v4
      - uses: Waterbottles792/PreMerge/github_action@main
        with:
          github-token: ${{ secrets.GITHUB_TOKEN }}
          # fail-above: "0.6" # optional risk gate
CI/CD Integration

Automated conflict prediction on every PR

Add three lines to your workflow and PreMerge posts a risk report on every pull request — and updates it in place on every push.

1

PR opened or updated

The action triggers on opened, synchronize, and reopened events.

2

Analysis runs

PreMerge fetches both branches and runs the full two-signal analysis. JSON output is written to disk.

3

Comment is posted

A formatted risk table is posted to the PR. On subsequent pushes, the same comment is updated — no spam.

4

Gate fires (optional)

If fail-above is set and the threshold is exceeded, the check fails after posting the comment — so developers always see the full report.
